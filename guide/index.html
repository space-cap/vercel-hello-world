또한 프롬프트 박스가 나올 때마다 우측 상단의 [복사] 버튼을 눌러 Claude, ChatGPT, 또는 Cursor의 채팅창에 바로 붙여넣어 보세요. 이 책의 프롬프트는 모두 실전에서 검증된 완성형입니다.

⚠️
이 책이 알려주지 않는 것
파이썬 문법, HTML 태그 의미, CSS 속성값. 이 책은 코딩을 가르치지 않습니다. 대신 코딩을 AI에게 위임하고, 비즈니스에 집중하는 법을 알려줍니다.

01

외주 개발의 불편한 진실:
개발자는 당신 편이 아니다

⏱ 약 4분·PART 1 · 마인드셋

창업 아이디어가 생겼을 때 가장 먼저 드는 생각은 "이걸 만들어줄 개발자를 찾아야겠다"입니다. 그것이 당신의 첫 번째 실수일 수 있습니다.

외주 개발사의 비즈니스 모델을 냉정하게 분석해봅시다. 외주사는 "빠르게 만들고 오래 관계를 유지하는" 것으로 수익을 냅니다. 즉, 초기 개발로 착수금을 받고, 이후 기능 추가·버그 수정·서버 유지보수 명목으로 지속적인 수익을 가져갑니다. 고객이 독립할수록 외주사의 수익은 줄어듭니다.

📖
실제 사례 — "견적서 지옥"
서울의 한 스타트업 대표는 2023년, AI 면접 코칭 플랫폼을 외주사에 의뢰했습니다. 최초 견적은 2,800만 원에 3개월이었습니다. 5개월이 지난 시점, "관리자 통계 페이지"와 "이메일 자동화" 기능이 추가되며 총 금액은 5,200만 원으로 불어났습니다. 결국 런칭 후 첫 유료 고객을 7명 모으는 데 그쳤고, 이 사업은 1년 만에 접었습니다.

외주 계약서에서 반드시 확인해야 할 3가지

01
소스코드 소유권 (IP Rights)

계약서에 "납품 완료 후 모든 지식재산권은 클라이언트에 귀속된다"는 문구가 없으면, 이론적으로 외주사는 해당 코드를 다른 고객에게 재사용하거나, 향후 법적 분쟁을 걸어올 수 있습니다.

02
기능 범위(Scope) 정의의 모호함

"회원가입 기능 구현"은 외주사 입장에서 이메일/비밀번호 로그인만을 의미합니다. 여러분이 생각한 소셜 로그인, 프로필 사진 업로드, 이메일 인증은 별도 견적 대상입니다. 모든 화면과 기능을 목록으로 명시하세요.

03
하자보수 기간 이후 유지보수 정책

통상 3개월의 무상 하자보수 기간이 끝나면 모든 수정은 유상입니다. 버튼 색상 변경 한 번에 10~30만 원의 청구서가 날아오는 게 현실입니다.

💡
바이브코딩의 답: 외주사의 이해관계와 무관하게, 대표님 본인이 AI와 1:1로 협업하여 제품을 만들고 직접 수정할 수 있어야 합니다. 이 책이 그 길을 알려드립니다.
✅ 실습 | 외주 견적서 리뷰 체크리스트

외주를 이미 받았거나, 향후 받을 계획이 있다면 아래 항목을 반드시 확인하세요.

02

"기능이 많을수록 성공한다"는
가장 치명적인 착각

⏱ 약 4분·PART 1 · 마인드셋

Facebook은 창업 초기, 사진 기능도 없었습니다. Instagram도 처음엔 위치 공유 앱이었습니다. Airbnb의 첫 버전은 에어 매트리스를 빌려주는 사이트였습니다.

성공한 제품은 처음부터 완벽했던 게 아닙니다. 오히려 핵심 하나에 집착했기에 살아남았습니다. 반면, 처음부터 모든 기능을 넣으려는 욕심은 프로젝트를 반드시 망하게 합니다.

Feature Creep(기능 비대증)이 벌어지는 과정

기능 비대증은 창업가의 불안에서 시작됩니다. "이 기능이 없으면 고객이 안 쓸 것 같다"는 공포가 다음 공포를 부르고, 개발 기간은 늘어나며, 비용은 불어납니다. 더 무서운 건, 그 기능들을 실제 고객이 쓰지도 않는다는 사실입니다.

리서치 데이터
초기 MVP 평균 핵심 기능 수1.8개
창업가가 처음 기획하는 기능 수평균 12개
실제 유저가 첫 달 사용하는 기능 비율전체의 20%

"이 기능이 없으면 고객이 돈을 안 낼까?" 테스트

기능을 기획할 때마다 스스로에게 이 질문을 던지세요. "이 기능이 없어도 고객이 결제할 의향이 있는가?" 만약 조금이라도 망설임이 있다면, 그 기능은 첫 버전에서 제거해야 합니다.

💡
실전 팁 — "버리기 결정 = 빠른 런칭"
기능을 한 가지 줄일 때마다 개발 기간이 평균 1.5일 단축됩니다. 3개를 버리면 4일이 남습니다. 그 4일로 마케팅을 하세요.
✅ 실습 | 킬러 기능 선발 워크시트

아이디어에서 생각나는 기능을 아래에 모두 적고, 각 기능마다 "이것 없으면 결제 안 할까?" 질문에 ✓ / ✗를 표시한 뒤, ✓가 붙은 기능 중 단 1개만 선택하세요.

기능명"없으면 결제 안 함?" (✓/✗)최종 선택

03

7일 스프린트 철학:
시장 검증은 1주일이면 끝난다

⏱ 약 3분·PART 1 · 마인드셋

파킨슨의 법칙(Parkinson's Law)은 이렇게 말합니다. "일은 주어진 시간을 꽉 채우도록 늘어난다." 개발 기간 3개월을 주면 3개월이 걸립니다. 7일을 주면 7일 안에 끝납니다.

이것은 단순한 격언이 아닙니다. 스탠퍼드 d.school의 디자인 스프린트, Google Ventures의 5일 스프린트, 그리고 수백 개의 1인 창업 성공 사례가 증명합니다. 강제된 마감은 완벽주의를 무너뜨리고 실행을 강요합니다.

7일 스프린트 데일리 타임박스

Day 1
아이디어 정제 & 기능 범위 확정 — 킬러 기능 1개, DB 테이블 2~3개, 유저 플로우 완성
Day 2
Cursor 환경 세팅 & 프로젝트 초기 구조 — .cursorrules 작성, 폴더 구조, 기초 UI 뼈대
Day 3
핵심 기능 바이브코딩 (1차) — 킬러 기능의 데이터 입출력 흐름 완성
Day 4
핵심 기능 바이브코딩 (2차) & UI 다듬기 — 에러 핸들링, 로딩 상태, 반응형
Day 5
토스페이먼츠 결제 연동 — 결제창 연동, 성공/실패 웹훅 처리
Day 6
Vercel 배포 & 도메인 연결 — 환경변수, 빌드 오류 수정, HTTPS 도메인
Day 7
QA & 첫 고객 초대 — 스마트폰 실제 결제 테스트, SNS 런칭 게시글 발행

04

아이디어 필터링:
3,000만 원을 날리지 않는 MVP 진단 기준

⏱ 약 4분·PART 2 · 기획

모든 아이디어가 MVP로 만들 가치가 있는 건 아닙니다. 만들기 전에 반드시 3가지 기준으로 필터링하세요.

01
돈을 낼 고객이 지금 당장 존재하는가?

친구들이 "완전 좋겠다!"고 해도 실제로 신용카드를 꺼낼 사람이 있는지를 확인해야 합니다. 런칭 전 5명에게 선결제(Pre-order)를 받을 수 있다면 검증 완료입니다.

02
핵심 기능 1개로 가치를 전달할 수 있는가?

30초 안에 "이 제품은 ○○○ 문제를 ○○○ 방법으로 해결해줍니다"로 설명이 안 되면, 아직 기획이 덜 된 겁니다.

03
7일 안에 배포 가능한 규모인가?

회원가입 + 핵심 기능 + 결제 = 최소 3개 흐름으로 줄일 수 있어야 합니다. 이 조건이 충족되지 않으면 아이디어를 더 쪼개야 합니다.

📋 PROMPT #1 — MVP 기능 필터링 프롬프트 
당신은 실리콘밸리 최고의 1인 SaaS 창업 전략가입니다.
내 아이디어: [여기에 아이디어를 1~2줄로 적으세요]

다음 MVP 필터링 기준으로 분석해 주세요:
1. 이 아이디어의 단 하나의 킬러 기능을 정의하세요.
2. 첫 100명의 고객이 돈을 낼 근거를 구체적으로 설명하세요.
3. 7일 안에 배포 불가능한 부가 기능을 모두 나열하고 '버려야 할 목록'으로 정리하세요.
4. 최종 MVP를 한 문장으로 정의하세요: "[대상]을 위한, [문제]를 [방법]으로 해결하는 서비스"
05

킬러 기능 추출 프롬프트:
군더더기를 걷어내는 AI 파트너십

⏱ 약 3분·PART 2 · 기획

기획의 핵심은 추가가 아닌 제거입니다. AI에게 "이것도 넣어줘"가 아닌 "이것을 빼도 되는가?"를 질문하는 창업가가 7일 안에 런칭합니다.

❌ 흔한 기획 (12개 기능)

  • 카드뉴스 생성
  • AI 카피라이팅

개발 기간: 4일 완성
📋 PROMPT #2 — 기능 제거 프롬프트 
아래는 내가 계획 중인 서비스의 기능 목록입니다:
[기능 목록을 줄바꿈으로 나열하세요]

다음 기준으로 각 기능을 분류해 주세요:
- MUST (없으면 첫 결제가 불가능): 반드시 Day 7 이전에 개발

최종적으로 MUST 항목만으로 구성된 Week 1 MVP 기능 목록을 만들어 주세요.

유저 플로우 & DB 설계:
비개발자도 3분 만에 완성하는 법

⏱ 약 4분·PART 2 · 기획

데이터베이스(DB)는 어렵지 않습니다. "어떤 정보를 저장하고, 누가 그것을 보는가?"라는 질문에만 답하면 됩니다.

카드뉴스 SaaS를 예시로 들겠습니다. 이 서비스에 필요한 DB 테이블은 딱 3개입니다.

📋 PROMPT #3 — DB 설계 자동화 프롬프트 
나는 다음 서비스를 만들 예정입니다:
[서비스 설명 1~2줄]

핵심 기능: [킬러 기능 1개]
결제 방식: 토스페이먼츠 단건 결제 (월정액 없음)

Supabase PostgreSQL 기준으로:
1. 이 MVP에 필요한 최소한의 DB 테이블 (2~4개)을 설계해 주세요.
2. 각 테이블의 컬럼명, 데이터타입, PK/FK 관계를 표로 정리해 주세요.
3. 절대로 초기 버전에 필요 없는 테이블이나 컬럼을 제안하지 마세요.

.cursorrules 전략:
당신의 제품을 AI가 영구적으로 이해하게 만드는 법

⏱ 약 5분·PART 4 · 외주 졸업

.cursorrules는 Cursor AI에게 "이 프로젝트는 이런 구조이고, 이런 방식으로 코딩해야 한다"는 영구 기억을 심어주는 파일입니다. 이것이 바로 외주 졸업 키트의 핵심입니다.

3가지 유형별 .cursorrules 전문 템플릿

📋 Type A — SaaS / 구독형 서비스용 .cursorrules 
# Project Type: B2C SaaS with Subscription
# Stack: Next.js 15, Supabase, Stripe or Toss (recurring billing), TypeScript

## Core Rules
1. Always preserve the subscription status check logic in middleware.ts
2. Never expose secret keys; always use server-side API routes for payment operations
3. Use Row Level Security (RLS) in Supabase — every table must have user-scoped policies
4. Write idempotent webhook handlers — duplicate events must be safely ignored
5. All UI text must be in Korean; all variable names in English

## Code Style
- Components: PascalCase (.tsx), Hooks: camelCase with 'use' prefix
- Always add loading and error states to async components
- Prefer Server Components; use Client Components only when user interaction is needed
📋 Type B — 마켓플레이스 / 단건 결제용 .cursorrules 
# Project Type: Digital Marketplace with One-time Payment
# Stack: Next.js 15, Supabase Storage, Toss Payments (one-time), TypeScript

## Core Rules
1. Payment confirmation must always happen server-side — never trust client-side callbacks
2. Download links must be generated server-side with signed URLs (15-minute expiry)
3. Supabase Storage bucket must be private — never public
4. Every purchase creates a record in the 'purchases' table before download is allowed
5. Handle Toss webhook idempotency using the payment orderId as a unique key

## File Upload Rules
- Max file size: 50MB per asset
- Allowed MIME types: PDF, ZIP, PNG, JPG, MP4
- Always validate file type on both client and server
📋 Type C — 콘텐츠 플랫폼 / 멤버십용 .cursorrules 
# Project Type: Content Platform with Membership Tiers
# Stack: Next.js 15, Supabase, Toss (recurring), TypeScript, MDX for content

## Core Rules
1. Gate premium content by checking user's active subscription tier in middleware
2. Never render premium content in the HTML for non-paying users — check server-side
3. Membership tiers: FREE | BASIC | PRO — always check the correct tier before rendering
4. All content is stored in /content/*.mdx — never in the database
5. Cache content pages with Next.js ISR (revalidate: 3600)

## Editorial Rules
- All article slugs must be in English, kebab-case
- Author attribution is required for every article
- Tag taxonomy must be consistent — no ad-hoc tags

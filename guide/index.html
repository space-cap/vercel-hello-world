30-SECOND DEFINITION

바이브코딩(Vibe Coding)이란 무엇인가?

"내가 만들고 싶은 것을 한국어로 말하면, AI가 코드를 짜주는 개발 방식."
프로그래밍 언어를 배울 필요가 없습니다. Python, JavaScript, SQL을 몰라도 됩니다. 대신 "사용자가 이메일을 입력하고 결제 버튼을 누르면 Supabase에 주문이 저장되고, 토스로 결제창이 열려야 해"처럼 비즈니스 로직을 말로 설명하면, Cursor나 Claude 같은 AI가 작동하는 코드를 만들어냅니다.

❌ 기존 개발 방식
  • 코딩 언어 6개월 독학
  • 외주사에 3,000만 원 의뢰
  • 6개월 뒤 MVP 런칭
  • 유지보수비 월 30만 원 지속 납부
✅ 바이브코딩 방식
  • AI에게 원하는 기능 한국어로 설명
  • 직접 Cursor로 7일 만에 구현
  • 토스 결제 즉시 연동, 라이브 런칭
  • 이후 유지보수도 AI와 단둘이 해결

01

외주 개발의 불편한 진실:
개발자는 당신 편이 아니다

⏱ 약 4분·PART 1 · 마인드셋

창업 아이디어가 생겼을 때 가장 먼저 드는 생각은 "이걸 만들어줄 개발자를 찾아야겠다"입니다. 그것이 당신의 첫 번째 실수일 수 있습니다.

외주 개발사의 비즈니스 모델을 냉정하게 분석해봅시다. 외주사는 "빠르게 만들고 오래 관계를 유지하는" 것으로 수익을 냅니다. 즉, 초기 개발로 착수금을 받고, 이후 기능 추가·버그 수정·서버 유지보수 명목으로 지속적인 수익을 가져갑니다. 고객이 독립할수록 외주사의 수익은 줄어듭니다.

📖
실제 사례 — "견적서 지옥"
서울의 한 스타트업 대표는 2023년, AI 면접 코칭 플랫폼을 외주사에 의뢰했습니다. 최초 견적은 2,800만 원에 3개월이었습니다. 5개월이 지난 시점, "관리자 통계 페이지"와 "이메일 자동화" 기능이 추가되며 총 금액은 5,200만 원으로 불어났습니다. 결국 런칭 후 첫 유료 고객을 7명 모으는 데 그쳤고, 이 사업은 1년 만에 접었습니다.

외주 계약서에서 반드시 확인해야 할 3가지

01
소스코드 소유권 (IP Rights)

계약서에 "납품 완료 후 모든 지식재산권은 클라이언트에 귀속된다"는 문구가 없으면, 이론적으로 외주사는 해당 코드를 다른 고객에게 재사용하거나, 향후 법적 분쟁을 걸어올 수 있습니다.

02
기능 범위(Scope) 정의의 모호함

"회원가입 기능 구현"은 외주사 입장에서 이메일/비밀번호 로그인만을 의미합니다. 여러분이 생각한 소셜 로그인, 프로필 사진 업로드, 이메일 인증은 별도 견적 대상입니다. 모든 화면과 기능을 목록으로 명시하세요.

03
하자보수 기간 이후 유지보수 정책

통상 3개월의 무상 하자보수 기간이 끝나면 모든 수정은 유상입니다. 버튼 색상 변경 한 번에 10~30만 원의 청구서가 날아오는 게 현실입니다.

💡
바이브코딩의 답: 외주사의 이해관계와 무관하게, 대표님 본인이 AI와 1:1로 협업하여 제품을 만들고 직접 수정할 수 있어야 합니다. 이 책이 그 길을 알려드립니다.
✅ 실습 | 외주 견적서 리뷰 체크리스트

외주를 이미 받았거나, 향후 받을 계획이 있다면 아래 항목을 반드시 확인하세요.

02

"기능이 많을수록 성공한다"는
가장 치명적인 착각

⏱ 약 4분·PART 1 · 마인드셋

Facebook은 창업 초기, 사진 기능도 없었습니다. Instagram도 처음엔 위치 공유 앱이었습니다. Airbnb의 첫 버전은 에어 매트리스를 빌려주는 사이트였습니다.

성공한 제품은 처음부터 완벽했던 게 아닙니다. 오히려 핵심 하나에 집착했기에 살아남았습니다. 반면, 처음부터 모든 기능을 넣으려는 욕심은 프로젝트를 반드시 망하게 합니다.

Feature Creep(기능 비대증)이 벌어지는 과정

기능 비대증은 창업가의 불안에서 시작됩니다. "이 기능이 없으면 고객이 안 쓸 것 같다"는 공포가 다음 공포를 부르고, 개발 기간은 늘어나며, 비용은 불어납니다. 더 무서운 건, 그 기능들을 실제 고객이 쓰지도 않는다는 사실입니다.

리서치 데이터
초기 MVP 평균 핵심 기능 수1.8개
창업가가 처음 기획하는 기능 수평균 12개
실제 유저가 첫 달 사용하는 기능 비율전체의 20%

"이 기능이 없으면 고객이 돈을 안 낼까?" 테스트

기능을 기획할 때마다 스스로에게 이 질문을 던지세요. "이 기능이 없어도 고객이 결제할 의향이 있는가?" 만약 조금이라도 망설임이 있다면, 그 기능은 첫 버전에서 제거해야 합니다.

💡
실전 팁 — "버리기 결정 = 빠른 런칭"
기능을 한 가지 줄일 때마다 개발 기간이 평균 1.5일 단축됩니다. 3개를 버리면 4일이 남습니다. 그 4일로 마케팅을 하세요.
✅ 실습 | 킬러 기능 선발 워크시트

아이디어에서 생각나는 기능을 아래에 모두 적고, 각 기능마다 "이것 없으면 결제 안 할까?" 질문에 ✓ / ✗를 표시한 뒤, ✓가 붙은 기능 중 단 1개만 선택하세요.

03

7일 스프린트 철학:
시장 검증은 1주일이면 끝난다

⏱ 약 4분·PART 1 · 마인드셋

파킨슨의 법칙(Parkinson's Law)은 이렇게 말합니다. "일은 주어진 시간을 꽉 채우도록 늘어난다." 개발 기간 3개월을 주면 3개월이 걸립니다. 7일을 주면 7일 안에 끝납니다.

이것은 단순한 격언이 아닙니다. 스탠퍼드 d.school의 디자인 스프린트, Google Ventures의 5일 스프린트, 그리고 수백 개의 1인 창업 성공 사례가 증명합니다. 강제된 마감은 완벽주의를 무너뜨리고 실행을 강요합니다.

📖
완벽주의가 죽인 창업 — 실제 사례
경기도 성남의 박OO 씨는 온라인 강의 플랫폼을 만들기로 결심하고, 2024년 초부터 기획서 작업에 들어갔습니다. 강의 업로드, 수강 기록, 수료증, 커뮤니티 게시판, 강사 정산 모듈까지 설계를 마쳤을 때 — 이미 5개월이 흘러 있었습니다. 개발을 시작도 하기 전에 에너지와 동기를 소진해 결국 사업을 접었습니다.

만약 "강의 1개 판매 → 토스 결제 → Zoom 링크 자동 발송"이라는 3줄짜리 MVP를 7일 만에 만들었다면? 실제 수강생 10명의 피드백을 받으며 살아남은 기능만 추가할 수 있었을 것입니다.

7일 스프린트 데일리 타임박스

Day 1
아이디어 정제 & 기능 범위 확정 — 킬러 기능 1개, DB 테이블 2~3개, 유저 플로우 완성. "이 기능이 없으면 돈을 못 받는가?"를 기준으로 판단.
Day 2
Cursor 환경 세팅 & 프로젝트 초기 구조 — .cursorrules 작성, 폴더 구조, Supabase 프로젝트 생성, GitHub 레포 연결.
Day 3
핵심 기능 바이브코딩 (1차) — 킬러 기능의 데이터 입출력 흐름 완성. UI는 못생겨도 OK. 데이터가 DB에 저장되는지만 확인.
Day 4
핵심 기능 바이브코딩 (2차) & UI 다듬기 — 에러 핸들링, 로딩 상태, 모바일 반응형. 스마트폰에서 작동하지 않으면 런칭 불가.
Day 5
토스페이먼츠 결제 연동 — 결제창 연동, 성공/실패 웹훅 처리. 이 날이 가장 중요하고 가장 많이 막히는 날.
Day 6
Vercel 배포 & 도메인 연결 — 환경변수, 빌드 오류 수정, HTTPS 도메인. 여기서 막히는 에러의 90%는 환경변수 누락이 원인.
Day 7
QA & 첫 고객 초대 — 스마트폰 실제 결제 테스트 완료 후 가장 가까운 지인 3명에게 링크를 보내 "써봐줄 수 있어?"라고 물어보세요. 그 3명의 반응이 사업의 첫 번째 시장 데이터입니다.
🔑
7일 스프린트의 핵심 원칙:
Day 7이 끝났을 때 모든 기능이 완벽하지 않아도 됩니다. 단 하나의 조건만 충족하면 됩니다. "첫 번째 고객이 실제로 카드를 긁을 수 있는가?" — 이것만 있으면 당신의 사업은 시작된 것입니다.

04

아이디어 필터링:
3,000만 원을 날리지 않는 MVP 진단 기준

⏱ 약 4분·PART 2 · 기획

모든 아이디어가 MVP로 만들 가치가 있는 건 아닙니다. 만들기 전에 반드시 3가지 기준으로 필터링하세요.

01
돈을 낼 고객이 지금 당장 존재하는가?

친구들이 "완전 좋겠다!"고 해도 실제로 신용카드를 꺼낼 사람이 있는지를 확인해야 합니다. 런칭 전 5명에게 선결제(Pre-order)를 받을 수 있다면 검증 완료입니다.

02
핵심 기능 1개로 가치를 전달할 수 있는가?

30초 안에 "이 제품은 ○○○ 문제를 ○○○ 방법으로 해결해줍니다"로 설명이 안 되면, 아직 기획이 덜 된 겁니다.

03
7일 안에 배포 가능한 규모인가?

회원가입 + 핵심 기능 + 결제 = 최소 3개 흐름으로 줄일 수 있어야 합니다. 이 조건이 충족되지 않으면 아이디어를 더 쪼개야 합니다.

📋 PROMPT #1 — MVP 기능 필터링 프롬프트 
당신은 실리콘밸리 최고의 1인 SaaS 창업 전략가입니다.
내 아이디어: [여기에 아이디어를 1~2줄로 적으세요]

다음 MVP 필터링 기준으로 분석해 주세요:
1. 이 아이디어의 단 하나의 킬러 기능을 정의하세요.
2. 첫 100명의 고객이 돈을 낼 근거를 구체적으로 설명하세요.
3. 7일 안에 배포 불가능한 부가 기능을 모두 나열하고 '버려야 할 목록'으로 정리하세요.
4. 최종 MVP를 한 문장으로 정의하세요: "[대상]을 위한, [문제]를 [방법]으로 해결하는 서비스"
05

킬러 기능 추출 프롬프트:

.cursorrules 전략:
당신의 제품을 AI가 영구적으로 이해하게 만드는 법

⏱ 약 5분·PART 4 · 외주 졸업

.cursorrules는 Cursor AI에게 "이 프로젝트는 이런 아키텍처이고, 어떤 파일도 함부로 지우지 말라"는 영구 기억을 심어주는 파일입니다. 이것이 바로 비개발자가 외주사에 평생 종속되지 않고 스스로 서비스를 운영할 수 있는 '외주 졸업 키트'의 핵심 비결입니다.

3가지 비즈니스 유형별 .cursorrules 실전 템플릿

📋 Type A — B2C SaaS / 월 구독형 서비스용 .cursorrules 
# Project Type: B2C SaaS with Subscription
# Stack: Next.js 15, Supabase, Toss Payments / Stripe, TypeScript, Tailwind CSS
# Role: Senior Fullstack Architect for a non-technical solo founder

## Core Architecture Rules
1. Always preserve the subscription status check logic in middleware.ts. Non-paying users must never access /dashboard.
2. Never expose secret keys; all payment operations and Supabase service-role calls must happen strictly in /app/api/*.
3. Use Row Level Security (RLS) in Supabase — every table must have user-scoped policies (auth.uid() = user_id).
4. Write idempotent webhook handlers — duplicate payment events with the same orderId must be safely ignored.
5. All user-facing UI text must be in polished Korean; code identifiers in clean English.

## Safe Modification Rules
- When the user asks for a UI change, only modify the specific component. Never rewrite the entire parent layout.
- Always provide the complete file without truncation or ellipses (...).
📋 Type B — 디지털 콘텐츠 / 단건 결제 마켓플레이스용 .cursorrules 
# Project Type: Digital Asset Marketplace with One-time Payment
# Stack: Next.js 15, Supabase Storage, Toss Payments, TypeScript, Tailwind

## Core Architecture Rules
1. Payment confirmation must strictly occur server-side — never trust client-side parameters.
2. Digital download links must be generated as temporary signed URLs (15-minute expiration).
3. The Supabase Storage bucket for paid files must be PRIVATE — never public.
4. Every valid purchase must insert a verified row in the 'orders' table before granting asset access.
5. Prevent duplicate downloads by checking order verification token in the API handler.
📋 Type C — 커뮤니티 & 유료 멤버십 플랫폼용 .cursorrules 
# Project Type: Community & Membership Platform
# Stack: Next.js 15 App Router, Supabase Auth & DB, Toss Recurring, Tailwind

## Core Architecture Rules
1. Gate premium content by inspecting user's active membership tier (FREE | PRO | VIP) server-side.
2. Never send blurred premium content HTML to non-paying users — fetch from DB only if authorized.
3. Optimize page load speeds using Next.js ISR (Incremental Static Regeneration) where possible.
4. Provide immediate visual feedback (loading spinners, optimistic updates) for all user actions.
💡
왜 기존 외주사는 .cursorrules를 주지 않을까요?
외주사의 핵심 수익원은 초기 개발비가 아니라 "런칭 후 매달 청구하는 유지보수 계약금과 사소한 수정 비용"입니다. 고객이 스스로 AI와 대화하며 버튼을 바꾸고 새 페이지를 추가할 수 있게 되면, 외주사의 밥줄이 끊기기 때문입니다.

VibeCraft는 정반대의 길을 갑니다:
우리는 대표님이 외주사 없이 100% 자립하는 것을 목표로 합니다. 7일 만에 완성된 제품을 넘겨드릴 때, 해당 프로젝트의 파일 트리와 데이터베이스 구조를 100% 학습시킨 [맞춤형 .cursorrules]를 함께 납품합니다. 대표님은 이것 하나만 Cursor 폴더에 넣어두면 평생 유지보수 비용 0원으로 서비스를 마음껏 진화시킬 수 있습니다.

유저 플로우 & DB 설계:
비개발자도 3분 만에 완성하는 법

⏱ 약 6분·PART 2 · 기획

데이터베이스(DB)는 결코 어렵지 않습니다. "어떤 정보를 저장하고, 누가 그것을 조회/수정할 수 있는가?"라는 2가지 질문에만 답하면 끝납니다.

카드뉴스 자동 생성 SaaS를 예시로 들어보겠습니다. 이 서비스가 실제로 돌아가는 데 필요한 DB 테이블은 딱 3개면 충분합니다.

📋 PROMPT #3 — 3분 DB 스키마 자동 설계 프롬프트 
나는 다음 서비스를 만들 예정입니다:
[서비스 설명 1~2줄]

핵심 기능: [킬러 기능 1개]
결제 방식: 토스페이먼츠 단건 결제 or 정기 구독

Supabase PostgreSQL 기준으로:
1. 이 MVP에 필요한 최소한의 핵심 DB 테이블 (2~3개)을 설계해 주세요.
2. 각 테이블의 컬럼명, 데이터타입(uuid, text, timestamp 등), PK/FK 관계를 명시해 주세요.
3. Supabase SQL Editor에 바로 복사-붙여넣기할 수 있는 CREATE TABLE SQL 스크립트를 작성해 주세요.
4. 불필요한 테이블이나 컬럼은 엄격히 배제하세요.

🚨 [보안 필독] 내 DB가 탈탈 털리지 않게 하는 RLS 1분 세팅법

바이브코딩 입문자가 가장 많이 저지르는 치명적 실수가 있습니다. Supabase에 테이블을 만들고 RLS(Row Level Security, 행 단위 보안 정책)를 켜지 않는 것입니다.

💣
RLS를 켜지 않으면 일어나는 참사:
Next.js 클라이언트에 공개된 Supabase 키(NEXT_PUBLIC_SUPABASE_ANON_KEY)를 이용해, 악의적인 해커가 브라우저 콘솔에서 supabase.from('payments').select('*') 한 줄만 치면 전체 회원의 결제 내역과 개인정보가 실시간으로 통째로 유출됩니다.

해결책은 너무나 간단합니다. 아파트 현관문에 도어락을 달듯, "자신의 데이터는 오직 본인(로그인한 유저)만 조회하고 수정할 수 있다"는 규칙을 걸어주는 것입니다.

📋 PROMPT #3-B — Supabase 철벽 보안(RLS) SQL 생성 프롬프트 
다음 Supabase 테이블들에 대해 가장 안전한 RLS(Row Level Security) 정책 SQL을 작성해 주세요.

테이블 목록:
- users (id, email, created_at)
- cards (id, user_id, keyword, image_urls)
- payments (id, user_id, amount, status)

보안 원칙:
1. 모든 테이블에 대해 ALTER TABLE [테이블명] ENABLE ROW LEVEL SECURITY; 적용
2. users 테이블: 로그인한 사용자(auth.uid() = id)만 본인 정보 조회 및 업데이트 가능
3. cards 테이블: 본인이 생성한 작업물(auth.uid() = user_id)만 조회, 추가, 삭제 가능
4. payments 테이블: 본인 결제 내역(auth.uid() = user_id)만 조회 가능. 결제 상태(status) 업데이트는 클라이언트가 조작하지 못하도록 오직 서버 서비스 롤(Service Role) 키로만 가능하게 차단.
5. 복사 후 Supabase SQL Editor에서 원클릭으로 실행할 수 있는 완성형 쿼리를 제공하세요.
💡
VibeCraft Insight: "외주사는 보안 사고가 터져도 책임지지 않습니다"
많은 프리랜서 외주 개발자가 납품 기한에 쫓겨 RLS를 귀찮다는 이유로 비활성화해 둡니다. 런칭 후 데이터가 유출되거나 조작되면 피해는 오롯이 창업가의 몫입니다. VibeCraft가 납품하는 모든 프로젝트는 이 RLS 보안 정책이 3중으로 기본 잠금되어 있어 안심할 수 있습니다.
